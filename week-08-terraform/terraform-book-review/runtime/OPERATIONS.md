## Exact non-secret configuration contract

Unknown/missing fields fail closed, except optional `release_authorized`, which defaults to **false**. It must be a JSON boolean, never a string/integer. No null/empty optional keys: omit keys not used by the tier. Configuration fields (tier-specific requirements are noted):

| Key | Contract |
| --- | --- |
| `release_authorized` | Optional strict boolean, default **false**; Terraform must supply false by default. Blocks bootstrap before downloads/local setup and every service before startup. |
| `tier` | `web`, `app`, or `initializer` |
| `region` | Commercial AWS region; every secret ARN must match it |
| `public_origin` | Approved `https://hostname` only, lowercase DNS, no port/path/trailing slash |
| `internal_url` | Approved `http://internal-alb-hostname` only, no port/path/trailing slash |
| `db_host`, `replica_host` | Distinct actual primary/replica DNS names; never loopback/IP/URL |
| `db_name` | Isolated schema, `[a-z][a-z0-9_]{0,47}` |
| `runtime_artifact_url`, `runtime_artifact_sha256` | **Web/App only:** plain public HTTPS URL without query/auth/redirect, operator-reviewed artifact's exact lowercase SHA-256. Omit both on initializer. |
| `rds_ca_path`, `rds_ca_sha256` | **App/initializer only:** exact path `/etc/book-review/rds-ca.pem` and its lowercase SHA-256. Preinstalled in the approved AMI, root-owned 0644 with root-controlled, traversable parent directories; no symlinks. No CA download. Omit both on Web. |

App additionally requires `app_secret_arn`, `app_secret_version`, `router_secret_arn`. Initializer additionally requires `app_secret_arn`, `app_secret_version`, `master_secret_arn`, `master_secret_version`. Web accepts **none** of these secret fields. Both version selectors are Secrets Manager **VersionId** values, 32–64 alphanumeric/hyphen characters, not AWSCURRENT or Terraform version counters. Use the same exact App version on all App nodes and the initializer; Terraform can resolve its secret-version resource version ID without reading the value. App/master requests include `--version-id` and verify the returned ARN and VersionId. Router alone uses the currently approved AWSCURRENT version; IAM is exact ARN, no cross-account redirects/endpoints or ambient profiles.

App SecretString JSON is exactly `{username,password,jwt_secret}`. Master is exactly `{username,password}`. Existing external Router secret is exactly `{certificate,private_key}` (unencrypted usable PEM pair). No credentials belong in config, artifact, user data, versions file, examples or logs. App DB password/JWT are passed directly in Python's private child environment, never shell/argv, environment files or log output. Only the service UID/root can inspect that process; suppress core dumps. AWS responses stay in memory. Router PEMs/config are mode 0600 in systemd's mode-0700 `/run/book-router` on checked tmpfs, destroyed at service stop/reboot. Private keys are never generated here.

## Dependency release interlock

The current pinned dependency set is **release-blocked**, not made safe by unchanged-source deployment. Parent records the public Next 15.2.3 advisory facts and applicability limitations. Setting `release_authorized=true` is only an operational interlock and must **not** be used to ship this known-vulnerable pin. A human-approved fixed upstream revision, updated provenance/lock review, compatibility/security review and the other release gates require separately authorized work outside this scope. Do not execute builds or deploy the current pin on the strength of this flag. The bootstrap itself never builds; its first action checks authorization before prerequisite commands, downloads or configuration changes. All services, including nginx, use a systemd ExecStartPre authorization check, and Python config loading refuses unauthorized operation. Secret reads, direct DB connections, artifact installation, initializer and supervisor also fail closed. Changing a running node's flag does not automatically stop existing processes: use the approved stop/replacement process.

Image optimization (`/_next/image`, including suffixes/query requests) is denied at nginx, and non-GET/HEAD requests outside the explicit needed API operations are denied. This is **defense in depth only**, not proof that any advisory is fixed or inapplicable; server actions are not used by the source. No JavaScript or lockfile patching occurred. Read-only upstream verification and non-executing artifact inspection remain available for offline preparation.

## AMI and build artifact contract

Supply a verified **Ubuntu 24.04 amd64** AMI with every dependency in `dependencies.json` preinstalled. No apt/curl-pipe/install fallback exists. Bootstrap checks Linux, amd64, OS release, systemd, tmpfs `/run`, root-owned immutable configuration, Node 22 LTS, npm 10, nginx >=1.24, Router 8.4, Python 3.12, PyMySQL 1.1.1 and AWS CLI 2. The version inspection function `bootstrap.runtime_versions()` returns an exact JSON map of `node,npm,nginx,mysqlrouter,awscli,python,PyMySQL`; bind the artifact to those actual versions. The AMI must have `/usr/sbin/nginx`, `/usr/sbin/useradd`, `/usr/bin/python3`, standard system tools, systemd-resolved's local DNS stub at 127.0.0.53 and a maintained OS CA store. Bootstrap invokes nginx/useradd by those explicit trusted absolute paths; its restricted `/usr/local/bin:/usr/bin:/bin` PATH is deliberately not expanded. Offline path tests fake both execution and account lookup; no OS user is created during validation. An approved image bake/patch pipeline is required; this repository neither creates nor verifies an AMI remotely.

A future separately approved Linux build uses `scripts/verify_upstream.py --extract-to <new-build-directory>` (or `runtime/upstream.py` on the instance tooling image). It verifies the 4,264,317-byte archive, both lock hashes and every selected unchanged source file **before** extraction. Tracked upstream node_modules, .env, Dockerfiles and irrelevant content are excluded. All archive entries, including excluded ones, are checked for links, traversal, duplicates, size/count/expansion limits and unexpected layout. No downloaded source is executed by the verifier.

In the isolated Linux build directory, after dependency/advisory review and explicit authorization, run `npm ci --ignore-scripts --no-audit --no-fund` in both frontend/backend with no credentials and build frontend using `NEXT_TELEMETRY_DISABLED=1 NEXT_PUBLIC_API_URL=<approved-public-origin> npm run build`. Preserve `.next` production server output, public assets, both installed dependency trees and unchanged source/package locks. No static export. Native dependencies and the upstream release's advisories remain release gates; do not patch/upgrade locks or JavaScript to force success. Changing origin requires rebuilding. A macOS build is not a Linux artifact.

The future packaging helper is `runtime/package_artifact.py --source <approved-build-directory> --public-origin <https-origin> --versions <non-secret-versions.json> --output <outside-source-bundle.tar.gz>`. It does not install/build anything. It flattens only file symlinks whose targets are inside that build (npm .bin), excludes env/VCS/credential paths, rechecks every original source hash, includes per-file hashes and requires Next server/build files. Symlinked dependency directories are unsupported. Review the output before publishing through an existing approved immutable HTTPS artifact location; publishing is not performed here. Bootstrap rejects archive links, extra source files, missing files, changed locks/source, wrong commit, platform/origin/toolchain or hash mismatch. Artifact pins attest to the operator's reviewed build; they do not independently prove which build environment produced bundled JavaScript. Bootstrap never downloads upstream dependencies or builds application code.

Bootstrap needs about 2.5 GiB free disk as a conservative fixed floor. Archive limits: 512 MiB compressed, 1.5 GiB expanded, 256 MiB/member, 100,000 entries. In-memory validation can require several GiB RAM: select adequate instance memory (8 GiB recommended for bootstrap) and reduce artifact content/size through a reviewed build if necessary. Installation is fail-closed and **not in-place upgrade/idempotent reinstallation**: an existing `/opt/book-review/application` aborts. Replace nodes with a reviewed ASG rollout; do not rerun over a partial install. No SDK creates/mutates infrastructure.

## Startup proof and lock barrier

At immutable upstream `84280063bea7ccd5144dafa2b969ec4e2e69ffbb`, `backend/src/server.js` awaits, in sequence:

1. DB authentication; User, Book, Review model construction.
2. `User.sync({alter:true})`, `Book.sync({alter:true})`, `Review.sync({alter:true})`.
3. `User.count()` and conditional awaited user seed; then Book count/seed; then Review count/seed.
4. Route module construction and mounting `/api/users`, `/api/books`, `/api/reviews`.
5. Finally `app.listen(PORT)`.

Thus a **new child owning the listener** plus successful required schema/API checks proves all awaited startup branches returned; a pre-existing listener or books-only response does not. Supervisor checks port 3001 is unoccupied before and after lock acquisition, records Linux `/proc/<pid>/stat` start ticks of its directly spawned Node, verifies all port-3001 LISTEN socket inodes belong to that same PID, reads all required columns for Users/Books/Reviews on the verified-TLS lock connection, GETs `/api/books` and `/api/reviews/<bookId>`, and exercises User.findOne via a fixed invalid login (expects 400 `Invalid email or password`; **no user is inserted or successful authentication claimed**). It rechecks identity and lock ownership before releasing. No JS preload/monkeypatch or fixture rows.

Lock names derive only from schema, so every App node and optional initializer serialize in the same primary. GET_LOCK waits in 3-second bounded calls for at most 60 seconds; startup deadline is 180 seconds. Direct MySQL connections verify both CA and hostname and never auto-reconnect a lost named-lock session. Lock loss/SQL failure/child death/schema failure kills the process group **before** releasing/closing a still-held lock. systemd bounds rapid failures to three starts per 900 seconds with 15-second backoff. Continued health failures (three 5-second cycles, each bounded probe) terminate Node; all restarts reacquire the lock. ALB checks `/api/books`, never `/`. Web `/healthz` checks Next and both internal books/reviews DB paths and returns 503 on failure, even if its own listener lives.

Named locks are advisory and session-scoped, not a distributed transaction coupling Node's separate SQL connections to the supervisor. On DB/network loss, detection is bounded by timeouts and Node is terminated; in-flight server-side SQL completion/failover behavior needs real cold-start/loss testing. Never manually run a second backend bypassing the service. New source ordering invalidates this proof and requires a new source review/lock. No live database barrier proof has been claimed.

## Database and TLS boundaries

Initializer is an optional, separately permissioned, disabled-by-default Terraform instance. It has only exact-version master/App read access and never the Router secret. Under the named lock, it checks account existence first. Only a missing account permits schema creation, plain `CREATE USER` with REQUIRE SSL (no `IF NOT EXISTS` race bypass), and schema-only `SELECT,INSERT,UPDATE,DELETE,CREATE,ALTER,DROP,INDEX,REFERENCES` grants. No ALTER USER, REVOKE or credential-reset path exists. It creates **no** users/books/reviews application rows. SQL values are bound; only validated identifiers/constant privilege names enter SQL structure. MySQL database-grant underscores are escaped when `partial_revokes` is disabled, preventing wildcard schema grants; with partial revokes enabled, the schema is literal.

An established account is **verification-only**: it must be the sole matching username at host `%`, require SSL, and have exactly USAGE plus the expected isolated-schema privileges, without other grants, roles or grant options. The initializer separately authenticates with the supplied App password using CA/hostname-verified TLS, selects the configured schema and verifies `CURRENT_USER()`. Any password/schema/identity/TLS/privilege mismatch fails without account or schema mutation. Never use an unrelated/shared account; password rotation and grant remediation require a separately reviewed process. New-account DDL is not transactional: partial setup after failure is not silently repaired on retry. RDS master metadata access, SHOW GRANTS formatting, MySQL grant semantics and effective privileges require future verification. No FLUSH PRIVILEGES or global admin grants are required.

Before every Python direct connection and Router startup, the preinstalled CA file's root ownership, non-writable-by-group/other mode, no-symlink path, bounded size and configured SHA-256 are checked. All Python direct connections, including initializer master/App verification, startup lock/schema and replica reporting, pass **only** `ssl=context` with `ssl.create_default_context(cafile=...)`, CERT_REQUIRED and check_hostname enabled. Do not add `ssl_verify_cert`/`ssl_verify_identity` arguments: pinned PyMySQL1.1.1 would replace that context and lose the pinned CA/hostname behavior. A narrow connection subclass rejects a server greeting without CLIENT.SSL **before any authentication packet**, then delegates TLS/authentication to the unchanged driver. It requires a negotiated SSLSocket using that exact context/hostname and a cipher before initial SQL and every subsequent command; a cached `_secure` flag is insufficient. The actual pinned driver's constructor, greeting parser and authentication code are exercised offline against memory transports, including zero authentication writes for missing SSL and only the non-authenticating SSLRequest when certificate verification raises. Successful TLS/SQL transports in those tests are fakes, not a real handshake or database. The adapter depends on pinned driver internals; any driver update requires renewed review/regressions. No installed package is modified. Node's upstream hard-coded `rejectUnauthorized:false` remains unchanged and is restricted to TLS over loopback `127.0.0.1:6446`. Router binds loopback, requires listener TLS, and uses REQUIRED + VERIFY_IDENTITY + the pinned CA for the actual RDS DNS target. No direct/unverified fallback. Real positive/negative CA/hostname tests and external listener PEM compatibility are release gates.

`report_replica.py` is an explicit future operator-only check, not an automatic boot action: App identity, replica DNS, verified TLS, require server read_only, read-only transaction, constant count queries only; no rows/credentials printed. It does not prove replication lag, failover or application read splitting. The unchanged application uses the primary only.

## HTTP, service and release gates

Next listens only on loopback 3000. Dedicated nginx runs non-root with only CAP_NET_BIND_SERVICE and port 80, no default AMI nginx site. Host plus ALB `X-Forwarded-Proto=https` must match the approved browser origin except the health endpoint. The ALB-only SG is essential: headers are not a replacement for network identity. Canonical `/api/*` and aliases map to `/api` exactly once; GET/HEAD books and per-book reviews, POST register/login and POST review only. Both forms of POST books and unknown API paths are denied. Only review POST forwards Authorization; all cookies and other Authorization headers are stripped. DB/server 5xx response bodies are intercepted and replaced with static failures. No redirect-following HTTP client, ambient proxy or unknown dynamic upstream is used. Internal ALB DNS is refreshed through the systemd-resolved stub. Plain HTTP exists only inside the approved VPC boundary; browser artifacts use HTTPS.

Services have distinct named non-root identities, root-owned source, mode-0700 runtime directories, systemd LoadCredential for the non-secret config, read-only filesystem protections, no privilege escalation/core dumps, sanitized Python stage output and suppressed raw Node/Router output. Only Next's `.next/cache` is writable application disk. Bootstrap returns **configured**, not healthy; future operators must independently check systemd/ALB/readiness status.

Before any cloud action: human approval of costs/identity, verified AMI/artifacts/dependencies, actual HTTPS origin/ACM, supplied secrets/PEMs, real SQL grants and concurrent startup tests, DB/failover/TLS negative tests, replica lag and all browser flows. Upstream sample rows are not human evidence and sample passwords are not usable signup credentials. Rotation requires a maintenance plan: coordinated MySQL dual-password transition using a separately reviewed authorized procedure, publish a new shared App VersionId, replace App nodes consistently, test, retire old password, and coordinate JWT re-login because upstream supports only one signing key. Do not rotate nodes independently; keep master separate and synchronize DB/master-secret changes. Remove initializer later only through human-reviewed Terraform, never self-termination.

It cannot clean up A2's agent or web-target VMs. No hosted run, federation exchange, canary deletion or workload-cleanup readiness is claimed.

The user selected cleanup independent of the Mac/Copilot session. Reuse of the saved PAT for separately approved agent registration remains allowed; cleanup does not consume it.

## Boundary and lifecycle

- Keep the existing **US$10 combined planning allowance**, not an enforced billing cap. Review current UK South/eu-west-2 prices, Blob storage/versions/transactions, network use and Azure Pipelines hosted-minute/parallel-job charges before bootstrap. An empty VPC/resource group is not proof the complete solution costs nothing. No live price or capacity guarantee is recorded here.
- Record one fixed UTC window, **at most 24 hours**, beginning with first provisioning, including control-plane preparation. In the protected config, use that start for `approved_at`, the same immutable `expires_at` everywhere, and `cleanup_at` at least **two hours before expiry**. Credential renewal, retries, canary success and later workload steps do not reset it. If the original window cannot fit the work and teardown, do not begin provisioning.
- Only the explicitly approved human IAM user and its two protective policies are retained persistently. This exception does not reset existing deadlines or authorize persistent cleanup roles, issuers, control-plane resources or VMs; operator privileges retain their original expiry.
- Budget and expiry fields are guards, not a scheduler or hard spending cap. Azure DevOps schedules are best-effort. Before arming, prove hosted availability and arrange monitored failure handling plus an independent, authorized teardown path within the window. A local reminder alone does not satisfy this gate.
- Bootstrap roots currently use local `.private/terraform.tfstate`. This is **not independent state custody or teardown**. A reviewed protected-state/teardown arrangement outside the disposable control group must exist before bootstrap; do not put its only recoverable state inside the storage account it must delete. Preserve necessary private receipts/state under an explicit retention decision before whole-account teardown. Seven-day Blob soft deletion is not permission to retain the control plane indefinitely.
- Never put workloads in the canary group/VPC. Azure resource-group deletion can cascade into children: the worker checks emptiness twice and the provider refuses nonempty groups, but these checks are not atomic with external writers. The protected environment lock serializes cooperating jobs, not other administrators. No other writer may use these namespaces during acceptance.
- AWS deletes only the exact lease/assignment-tagged VPC in `eu-west-2`. The worker checks subnets, interfaces, gateways, endpoints, peerings and transit attachments, and permits only the single default security group, ACL and main route table. The runtime role cannot remove unexpected children; fail closed and investigate rather than broadening permissions. Regional `Describe*` and Azure subscription/resource-group metadata reads are intentional and broader than the delete scopes. Azure discovery reads survive deletion of the canary-scoped role assignment, allowing a meaningful absence check.
- Do not import, replace or destroy an existing/shared AWS OIDC provider. A provider for the same issuer is account-wide; this template creates a new, exclusively owned provider. An existing one requires a separate reviewed reuse/ownership design, not a second attempted bootstrap.

## Real acceptance, failure handling and credentials

A valid acceptance record identifies actual definition/revision, immutable GitHub source commit, fixed lease/expiry, job start/end, real identities and scheduler timing. It requires:

- A successful fresh Azure WIF login and AWS `AssumeRoleWithWebIdentity` exchange into the exact restricted role/account; wrong subject/audience/account/lease must fail without deleting anything.
- Both canaries existed in their protected states/inventories, and actual validated destroy plans each reported **one cloud deletion**. Creation, update, replacement, import, move, deposed, unexpected-resource and incomplete/deferred plans are rejected. The worker applies the validated **saved plan**, not a new auto-approved plan.
- Empty managed state **and independently checked cloud absence** after cleanup. A successful subsequent zero-deletion retry is useful idempotency evidence, not a substitute for the first real deletion.
- AWS authentication/cleanup failure does not skip the Azure attempt. A failed/absent receipt is not success. Require failure alerts, state-lock recovery, cancellation/timeout behavior and continuation while the controller is unavailable. The two canary states currently share the Azure storage failure domain; do not mistake them for independent backend availability.
- Only allowlisted receipts are uploaded to the private `receipts` container and printed. Every receipt states `workload_cleanup_ready: false`. No state, binary/JSON plan, assertion, key or raw provider log is a public artifact. Genuine assignment screenshots/reflections are separate and remain pending.

The worker uses a private temporary assertion file for its own AWS STS invocation, then removes it. It clears inherited profiles/controller credentials, disables metadata credential discovery, captures command output and emits fixed failure codes rather than raw diagnostics. Terraform timeouts first request graceful interruption to persist state/unlock, then stop only that invocation's process group. Hard cancellation or an unavailable runner/backend can still leave a lock: **never automatically force-unlock**. An authorized operator must confirm the owning job/process has ended, inspect the exact lock/state privately and approve recovery before retry. No forced unlock or direct cloud deletion is implemented.

Native `AzureCLI@2` performs its own WIF login and credential caching. `set +x`, `visibleAzLogin: false` and an isolated CLI directory reduce disclosure; they are **not a claim that native-task internals never place tokens in process arguments**. Review the actual installed task's handling before arming. `AGENT_ID`/`TF_BUILD` are context checks, not cryptographic proof of Microsoft hosting. Isolation depends on the trusted reviewed YAML, restricted service connection/Secure File, fresh hosted VM and no untrusted code sharing the job. Do not debug with shell tracing or publish full environments/CLI logs.

Azure Architecture and the Evidence Needed to Prove It: Week 07

Eze Favour · DMI Week 07 · Updated 26 September 2026

My Week 07 Azure work now has a verified recovery behind it. An earlier repository review found 60 screenshot references: 38 files were missing and the other 22 were only one pixel. The correct response was to revisit the deployments, test their behavior and replace the evidence. Codex performed that recovery under my delegation and helped prepare this reflection from the recorded results. This article describes the new verification, not reconstructed historical execution.

Follow the request through three tiers

The recovered Book Review app has a public Azure load balancer, two private web VMs and two private API VMs across two availability zones. The web tier forwards same-origin API requests through an internal load balancer. The API connects to MySQL Flexible Server through a private subnet and DNS zone. Application VMs retrieve secrets using managed identities and Key Vault; credentials are not included in the repository or screenshots.

Each boundary has a job. Web servers can reach the private API, while the database accepts the required application sources. Network checks confirmed that the web node could not reach MySQL directly, that the application node could, and that the public entry points did not expose the API or database ports. Those tests support the configuration exports; a timeout alone would not establish the entire security posture.

A working API is only part of a working application

The initial HTTP tests passed, but browser testing found a real frontend defect: the homepage requested /api/api/books and displayed no books. The recovery changed it to use the same API helper as login and reviews. A screenshot review then revealed another issue: dark browser preferences produced white text on light cards. The final UI uses consistent readable foreground colors.

After these fixes, the browser displayed all three books. A synthetic test account logged in, submitted a review and still saw that review after reloading. An independent SQL query confirmed the exact stored row. This is a useful lesson from the recovery: a successful HTTP response cannot replace checking what a user actually sees and does.

Verify each smaller Azure exercise too

The original React VM remained available. Its Node and npm versions, Nginx configuration and restricted SSH rule were checked; a fresh production build succeeded in a separate directory. A nested route loaded after a hard refresh. The existing application and its original displayed deployment date were preserved rather than overwritten with a fictional new deployment history.

Mini Finance was deployed through Azure Storage static website hosting. All 32 published assets returned HTTP 200 and matched the source bytes. The original financial figures and profile are template data, not my personal finances. The temporary networking exercise demonstrated the specified three subnets and Nginx through a public load balancer, then its resource group was deleted after evidence capture.

EpicBook runs behind Nginx on a separate VM and uses its own database and restricted user on the shared private MySQL server. Its browser flow added a book to a cart and saved demo order 2. SQL independently confirmed the order. This is explicitly a demonstration: no payment was taken and no shipment was initiated.

Measure availability within a stated scope

The Book Review availability test stopped Nginx on one web server, waited 25 seconds for health probes to converge, then received 12 successful database-backed responses through the other server. The stopped service was restored, and subsequent requests observed both nodes again. An Azure Monitor health alert and real metric samples accompany the result.

That result has limits. It does not prove zero interruption during probe convergence or cover a database failure. The public app uses HTTP, and MySQL is a single instance with seven-day backups and no high-availability standby. Backup restoration was not tested. Calling this a production-style learning deployment is accurate; calling it fully production-ready would overstate the evidence.

Keep AI auditing separate from remediation

Claude Sonnet 4.6 through AWS Bedrock produced a plan before the Azure audit script existed, then ran the read-only audit skill before and after remediation. The four checks covered broad administrative ingress, public blob access, managed-disk encryption and MySQL public networking. Missing query data is not allowed to silently become a passing result.

The baseline finding was deliberately created on an unattached NSG, so it exposed no VM. The separate Codex operator narrowed its SSH source to one controller address; the fresh report passed all four checks. The original model responses remain available, including denied extra command syntax and corrected mistakes about Azure rule names. AI explanations need verification just as deployment claims do.

Make evidence useful to a reviewer

The submission now replaces the 60 original image references and adds two current account views. Native portal/app captures are distinguished from labelled recordings of genuine command, SQL and Claude output. Each slot has source information, dimensions and a file hash. Technical checklists are updated only where the results support them.

Current subscription access cannot prove historical Free Trial signup or agreement acceptance, and delegated remediation is not personal learner execution. Those distinctions remain visible. DMI controls rubric acceptance and scores; this recovery does not claim new marks. My practical takeaway is to connect every claim to an inspectable source and test the entire user flow before declaring completion.

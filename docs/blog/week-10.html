Two Pipelines, One Verified App: DMI Week 10 with Azure DevOps

Eze Favour · Published 25 September 2026 · Updated 26 September 2026

My Week 10 DevOps Micro Internship portfolio now includes a self-hosted Linux agent, static and React CI/CD deployments, and EpicBook deployed through separate infrastructure and application pipelines. This work is part of Pravin Mishra’s DMI programme. Codex performed the deployment and checks under my authorization; this article is an AI-assisted account of actual results.

Prove the agent before using it

The dedicated Azure DevOps agent runs on Ubuntu as the non-root azdoagent account. The official 5.279.0 agent package was verified, the service registered in the DMI-Week10-A1 pool, and a manual validation pipeline succeeded. Its checks included operating-system details, the effective user and free disk space: about 29 GB was available at that check.

For the EpicBook infrastructure pipeline, the agent’s managed identity is scoped to the assignment resource group and the Terraform state account. Private SSH keys and database secrets remain in the appropriate protected pipeline resources. AWS credentials were not copied to the build agent.

Verify both manual delivery and automatic CI

The static site is hosted on AWS EC2. Manual run 13 succeeded with Azure DevOps native SSH and file-copy tasks. A later source change triggered automatic CI, and run 17 passed with Eze Favour visible in the final page.

The React application is hosted on Azure. Manual run 12 and automatic CI run 16 passed the Build, Test, Publish and Deploy stages. The pipeline ran the actual Jest tests, built the production artifact, transferred it through the configured SSH connection and verified the deployed content. The upstream NodeTool task emits deprecation warnings; those warnings are recorded even though the runs succeeded.

A transport configuration issue was caught during delivery: literal backslash-n suffixes had reached generated host-trust and account files. The templates were corrected to use real YAML literal blocks and only the affected assignment-owned files were repaired. Host verification stayed enabled. This illustrates why a failing safety check should lead to correcting the configuration, not bypassing the check.

Separate infrastructure from application releases

The infra-epicbook repository holds Terraform and its pipeline. A reviewed plan led to successful apply run 11, provisioning the frontend and backend VMs, private managed MySQL, subnets, security rules and DNS. Terraform state lives in Azure Storage with versioning and recovery protections.

The four non-secret outputs were copied into the application handoff: public frontend address, backend SSH address, private backend address and MySQL hostname. This was an operator-performed handoff under delegation, not a claim that I personally carried it out.

The theepicbook repository holds the application and Ansible pipeline. Run 14 succeeded. Public Nginx forwards application traffic to the private backend on port 8080; PM2 manages Node and the database connection verifies TLS. Both frontend and backend reported changed=0 on the unchanged second Ansible run, with no failed or unreachable hosts.

Test the workflow, not just the home page

Nineteen meaningful HTTP and SQL checks passed against this deployment. They verified isolated carts, invalid-input rejection, transactional order persistence, retry-safe checkout and decimal-price preservation. An additional real browser checkout saved demo order 2. These are synthetic orders with no payment or shipment.

A controlled failure with a bounded recovery

The triage baseline selected successful infrastructure run 11 and application run 14. The operator created a temporary triage-safe-drill branch and inserted one Build step that printed a controlled-failure marker and exited 1. Run 18 failed before deployment, and the read-only triage tool fetched actual pipeline metadata, timeline records and failed-step logs. Its report classified the incident as APPLICATION and returned exit 1.

The operator removed only that injected step. Recovery run 19 passed Build, while Deploy stayed skipped because the branch was not main. A second triage returned HEALTHY, exit 0. The deliberate failure never reached main or changed the live application.

Update, 26 September 2026: AWS access was restored and the actual Claude Code/Bedrock triage workflow completed. Claude read fresh evidence for the healthy baseline, diagnosed controlled failure run 20 as APPLICATION/INCIDENT, and verified recovery run 21 after Codex removed only the injected step. Deployment stayed skipped on the drill branch. A stale-report issue found in the first attempt was corrected with a session timestamp guard; seven classifier/guard tests now pass. The accepted Claude responses and before/after reports are saved in the repository. The replacement kit remains identified as original, and learner-personal/manual evidence requirements remain for assessor review.

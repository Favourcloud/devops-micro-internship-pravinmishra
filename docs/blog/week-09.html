From Four Linux VMs to a Repeatable EpicBook Deployment: DMI Week 09

Eze Favour · Published 25 September 2026 · Updated 26 September 2026

Week 09 of my DevOps Micro Internship portfolio now includes live Ansible deployments, a private managed database, repeatability checks and an evidence-based AI risk review. This work is part of Pravin Mishra’s DMI programme. Deployment and verification were carried out with Codex under my authorization; the technical notes below are AI-assisted and describe recorded results.

Start with connectivity, then prove the configuration

The ad-hoc lab used four Azure Linux VMs grouped as web, app and database hosts. SSH, cloud-init and Ansible connectivity were checked before configuration. All four hosts returned successful ping results. The lab then ran uptime checks, installed htop, and installed and verified Nginx on the web hosts.

The static website exercise separated installation, deployment and HTTP verification into three plays. Both web servers returned HTTP 200, displayed Eze Favour and Group 1, and passed an unchanged second run with changed=0. After evidence was collected, all 23 resources belonging to this temporary lab were removed and their absence verified. Its old IP addresses are not current demo links.

Use Terraform for infrastructure and Ansible for configuration

MiniFinance is running on an Azure VM provisioned with Terraform and configured with Ansible. The playbook installs Nginx, deploys the pinned website source and verifies HTTP behavior. Its unchanged second run also reported changed=0. Capacity restrictions required an F1als_v7 VM in Sweden Central instead of the brief’s B1s size; that substitution is documented rather than hidden. The website’s names, balances and transactions are template demonstration data.

The EpicBook deployment goes further: Nginx is the public entry point, PM2 manages Node, and Azure Database for MySQL is reached over private networking with TLS certificate and hostname verification enabled. The app VM remains in UK South. Azure rejected managed MySQL provisioning there, so the database was deployed in Sweden Central with private network peering and DNS links. Port 3306 was not opened to the internet.

A working home page is only the beginning

Checkout testing exposed gaps in the original sample application. The disclosed patch isolates browser carts with signed membership, rejects invalid book IDs, preserves decimal prices, persists orders transactionally and makes retries return the existing order instead of creating duplicates. Checkout is a synthetic demo: no payment is taken and no shipment is arranged.

The managed-database migration preserved the earlier demo orders. Twenty actual HTTP and SQL checks passed, including cart isolation, order persistence, replay behavior, cross-origin rejection, sensitive-path rejection and verified database TLS. PM2 showed the application online, Nginx was active, and the backend responded on port 8080. A second unchanged Ansible deployment reported changed=0, failed=0 and unreachable=0.

Review predicted changes before applying them

The Week 09 risk exercise used real Claude Code through AWS Bedrock. Claude first produced the four-category plan, then reviewed a LOW baseline. A controlled removal of an explicitly disposable marker produced one predicted change and a HOLD finding. Codex separately checked the target and applied the reviewed change under delegated authorization; Claude did not apply it. A recovery review returned LOW.

This distinction matters: delegated operator execution is not a claim that I personally typed the manual apply command. The later managed-database deployment also passed a fresh deterministic check-mode review with zero changes. That later report is labeled separately because the AWS session expired before a fresh Claude call could run.

What this demonstrates

The main lesson from the recorded work is to verify each layer independently. Infrastructure state, SSH reachability, configuration convergence, HTTP behavior and database persistence answer different questions. Check mode predicts changes; it does not prove checkout works. A green first deployment is stronger when the unchanged rerun makes no changes and a real order survives in the database.

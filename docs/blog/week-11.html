Smaller Images, Recoverable Data: My DMI Week 11 Docker Build

Eze Favour · Updated 27 September 2026 · Assisted work disclosed

My Week 11 DevOps Micro Internship submission brings together Docker builds, networks, storage, image distribution and an EpicBook deployment on AWS. It is part of Pravin Mishra’s DMI programme. Codex performed the implementation and validation under my authorization, and Claude Code through AWS Bedrock provided read-only hardening analysis. This reflection is an assisted account of the recorded results, rather than a claim that I personally typed every command.

Make the runtime smaller and more deliberate

The React single-stage image measured 854,614,809 bytes. The multi-stage version measured 94,232,874 bytes: an 88.97% reduction. The build stage installs the Node toolchain and produces static assets; the final Nginx stage only needs those assets and its runtime. Copying dependency manifests before application code preserves a useful build-cache boundary. The resulting image runs as a non-root user, has a healthcheck and uses a read-only filesystem. A smaller image reduces distribution size and shipped components, but does not by itself prove security or a faster measured deployment.

The image is published to Docker Hub as favourcloud/my-react-app:week11-20260926. It was pulled by its immutable digest and started on the second VM, independently of the original build host. That makes the distribution exercise verifiable beyond a successful push message.

Networks and volumes need behavior tests

The networking exercises covered Docker’s default bridge, custom bridge, multiple networks and host mode. Container-name resolution worked on the custom network. The three-tier exercise inserted and retrieved a real MongoDB document, while the frontend could not resolve the database through its own network. MongoDB 8.0 initially failed on the host kernel, so the working exercise uses MongoDB 7.0 and records that change.

Bind-mounted Nginx logs survived removal of their container. A named volume also connected a writer to a read-only reader: the initial message and two subsequent updates appeared in the browser. This is stronger evidence of persistence than merely showing a volume in a list.

Recovery matters as much as startup

EpicBook now separates frontend, backend, reverse proxy and MySQL services in Docker Compose. The frontend does not receive database credentials, and MySQL has no published host port. Healthchecks and startup dependencies help establish readiness. The backend uses signed carts and transactional demo checkout, with independent SQL checks confirming stored orders and decimal totals. No payment or shipment occurs.

The reliability exercise stopped the backend and then the database. The frontend returned a retry message and the application recovered after the dependencies were restored. A cold database snapshot was restored into an isolated clone, and its catalogue, cart and order counts matched the original. An early script-input problem meant the first command’s exit status was insufficient proof; a separate comparison and cleanup completed the verification. A verified off-host copy of the snapshot is retained privately.

Give AI evidence access and review its advice

Claude Code ran an actual read-only planning workflow and the /docker-audit skill through Bedrock. A separate training copy of the EpicBook backend deliberately omitted USER and HEALTHCHECK and used latest. Its audit returned three failures. Codex reviewed the recommendations, applied the Dockerfile changes outside Claude, rebuilt and obtained six passes. The public service was never weakened to create this demonstration. Generic advice about healthchecks, running state and mutable version tags needed correction; those corrections and raw responses remain available for review. The earlier attempt had a script draft before planning. A fresh rerun on 27 September corrected that order: Claude inspected while no audit script existed, then the script and skill were created, the operator rebuilt the training container, and the final audit passed all six checks. Fifteen behavior tests passed. Direct editor and live terminal screenshots document all eleven audit evidence slots; the earlier attempt remains archived. Delegated execution is explicitly disclosed.

The most useful lesson from these results is to connect each operational claim to a behavior test: a working cart, a database record, a recovered service, or restored data. The app uses an AWS-provided CloudFront HTTPS address, but the origin hop remains HTTP and the stack is on one host. It is a teaching deployment, with those production limitations stated clearly. Optional CI/CD was not selected. The demo remains online at my request until I ask for cleanup.
